### 结构补充核验

切回原服务后，`joint-local-recovery.ps1 -Mode VerifySchema` 在内存解密原 custom-format
备份，使用 `pg_restore --schema-only --file=-` 只输出 SQL（不执行），与恢复库的
`pg_dump --schema-only` 比较。三套数据库均通过，覆盖导出的表、约束、索引、函数、
对象所有者、对象授权及 SQL 注释，不只比较应用模型或表行数。

首次省略显式输出选项时工具拒绝运行；修正后发现 PostgreSQL 重解析会把 varchar
枚举数组的整体 text[] 转换写成逐元素 text 转换。业务库的枚举 CHECK、Logto两个
邮件日志索引条件属此情形。比较器只统一 CHECK/索引中简单枚举字面量的该种转换，
保留全部枚举值、顺序和其余 SQL；另忽略工具版本头和随机 psql restrict 标记。
不忽略其他 SQL、授权或函数差异，也不修改数据库来让比较通过。
这不是恢复后的三库逐字节相同证明；不覆盖未被数据库 dump 收录的集群/宿主机配置。

## 失败及纠正（保留现场）

首次项目 `trade-joint-restore` 以 postgres 初始化、另建 logto 同名超级用户。
恢复原 GRANTED BY logto 授权时 PostgreSQL17 拒绝：原授权者必须具备目标角色 ADMIN option。
仅切换 SET ROLE 也未解决。没有删除角色、忽略错误、补授额外权限或篡改原备份。

确认源初始化角色 OID均为10后，使用全新 v2 卷，以源角色 rehearsal/logto 初始化。
仅跳过已由初始化创建的那条 CREATE ROLE，保留 ALTER ROLE（含密码属性）和原 GRANT。
该方式恢复成功，并再次比较完整角色声明和授权。首次失败容器已停止，卷保留。
脚本不提供任意跳步恢复或覆盖已有目标的旁路。

## 自检与限制

- 加密工具9项自检通过：同用户还原、错误 purpose、篡改、磁盘密文还原、拒绝覆盖、
  二进制进程捕获、失败子进程、大小上限、1MiB双向二进制传输。
  输入写入与输出读取并行，写完即关闭输入，避免管道相互等待；抑制异步写入返回值，
  防止 PowerShell 输出混入二进制结果。真实已存在备份/目标的重复执行均被拒绝。
  CurrentUser 是实际调用的 OS 保护范围；未创建第二 Windows 用户做跨用户攻击测试。
- 四个 PowerShell 文件语法检查通过；环境未安装 PSScriptAnalyzer，不冒充其 lint 通过。
  Python 核验器 Ruff/format、严格 mypy（连同应用211文件）通过，实际恢复核验通过。
  初次 Python 核验因挂载层级不符合旧核验器路径约定失败，修正只读挂载后通过。
- 代码简化复核保持显式固定目标、独立阶段与防覆盖检查；去掉未能解决授权问题的
  临时角色阶段续跑路径，没有为方便重跑而放宽保护。
- 后续将结构归一化抽成独立纯函数，减少恢复脚本嵌套并允许单独测试。
  10项比较器测试通过，包含等价 CHECK/索引转换及真实枚举值、索引列、GRANT、OWNER、
  SQL正文、注释变化仍被检出；加密9项复跑通过。抽取纯函数后三库结构及两组原角色
  授权最终只读复跑通过；六个相关 PowerShell 文件语法检查通过。
- 验收文档通过直接调用本地锁定 Prettier 检查。最初 `pnpm exec prettier` 未找到
  命令入口，使用已有安装文件调用成功；未重新安装依赖或改动系统环境。
- 每包64MiB内存上限适用于当前小型本机样例，超限明确失败。内存缓冲尽量清除，
  不承诺 OS 页面文件、进程内不可变字符串或 Docker 运行时环境的密码学擦除。
- DPAPI 依赖当前用户配置与密钥；系统重装、用户配置丢失或某些密码重置方式可能导致
  无法解密。同一用户权限下的恶意程序不在其隔离边界内。不能替代异机或异地加密灾备。
